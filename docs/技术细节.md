# 技术细节与实测记录

README 只讲怎么用；这一页讲**为什么这么写**，以及在长江雨课堂上实测踩到的坑。
每条都是真跑出来的，不是推测。看代码时对应的函数 docstring 里有更细的注。

---

## 1. 为什么是"长江雨课堂专用"

`changjiang.yuketang.cn` 与 `www.yuketang.cn` 的前端**同源**（同一份 `login.js`、`/v2/web/index` 逐字节一致），
所以走新版（COMMONUI）那套 DOM。

但上游按通用雨课堂写的选择器在这站会踩到三件事：

- **小节列表要点一下才渲染。** 列表在"学习报告"标签页下，**必须先点 `#tab-student_school_report`**，
  否则 `study-unit` 数量为 `0`，脚本会以为这门课没有视频。
- **原生 `.click()` 会抛异常。** 元素明明在、也可见，`.click()` 却抛 `ElementNotInteractableException`。
  统一改走 JS 点击。
- **完成度不是"已完成"三个字。** 这站显示的是百分比，实测文本形如
  `视频 国防概述1 2026-10-11 16:34 9.8% 详情 0.000/0.476`，里面根本没有"已完成"。
  上游那套"文本里找'已完成'"的判断在这里恒为假，会把**已经刷完的视频反复重播**。
  现在的判定改成解析 `complete-td` 里的百分比。

## 2. 挂着跑一整晚，得扛住这几种意外

### 2.1 结束判定不能只有一个

上游只有一条判据：给 `<video>` 挂监视器，`currentTime` 变小就当播放结束（播放器循环时会命中）。

问题是不循环、播完就停的情况下这条**永远不触发**，挂后台就会无限等下去。现在有三条：

1. `currentTime` 回退（原判据，保留）
2. `video.ended` 或 `currentTime` 接近 `duration` —— 显式判断播完
3. **5 分钟没有任何前进** —— 兜底放弃这一集、跳到下一个

第 3 条是挂后台的关键：最怕的不是报错，是把整晚耗在同一个视频上。

### 2.2 单轮异常不能带走整个任务

连续 3 轮抛异常才停，停之前每轮都会退回课程页重来。
另外 `PLAYED_TITLES` 会**在选中时就把标题登记进去**，所以就算完成度解析失败，也绝不会原地打转。

### 2.3 误报"全部播放完毕"（踩到过，比较严重）

实测遇到：课程页偶尔先吐出 80 多个**空的 `study-unit` 骨架**，标题稍后才填上去。
如果这时候正好取到，标题就是空串，而空串一旦被写进 `PLAYED_TITLES`，
下一轮所有同类小节都会被判成"已经播过"，最后**打印"恭喜你！全部播放完毕"，其实还剩几十个没刷**。

现在三层防线：

1. `video_title()` 区分两种情况 —— 「元素不存在」（旧版 UI，走 `unit.text` 兜底）
   与「元素在但文本为空」（渲染未完成，如实返回空串）；
2. `_units_rendered()` 渲染守卫 —— 小节列表拿不到标题就重载课程页重来（最多 3 次）；
3. `finish1video()` 拿到空标题直接 `return None`，**绝不写进 `PLAYED_TITLES`**；
   主循环把 `None` 计入 `no_progress_rounds`，连续 3 轮毫无进展就中止，并明说"这不是刷完了"。

### 2.4 窗口卡死 20 秒（`failed to close window in 20 seconds`）

上游方案是「点标题 → 站点开新标签页 → 播完 `driver.close()`」。
这站实测 `close()` 会偶发卡死 20 秒：

```
unknown error: failed to close window in 20 seconds
```

窗口状态一乱，后面几轮全部作废。

**根因不是在 `close()` 本身。** 实测视频页的 `window.onbeforeunload` 是 `null`，
单独调 `driver.close()` 只要 0.0 秒。真正的冲突是脚本自己注入的
「`pause` 事件 → 立刻 `play()`」这段防刷续播监听：页面卸载时它会和卸载流程互相顶。

现在的处理是两条：

- **根本不开新标签页。** 点标题前先注入脚本收编站点自己的 `window.open`，把视频 URL 截下来，
  然后在当前标签页 `driver.get()` 直达视频页。全程只有一个窗口，没有 `close()` 可卡。

  > 细节：`window.open` 必须返回一个**假窗口对象**（带 `focus` / `close` / `location`）。
  > 直接返回 `null` 会让站点内部抛错，可能连 URL 都不给你。

- **离开前先拆干净自己。** `leave_video_window()` 第一步永远是置 `__ytDone = true`、
  `clearInterval` 掉注入的定时器、清 `window.onbeforeunload`，再谈窗口怎么处理。
  `back_to_course_page()` 也加了上限（3 次），`close()` 失败就导航到 `about:blank`，绝不无限重试。

### 2.5 浏览器渲染进程会自己崩掉（挂后台的头号杀手）

这是实测中最难缠的一个：**播到几分钟后，Edge 的渲染进程会整个崩掉**，主循环抛
`WebDriverException: Message: tab crashed`，无头模式下直接报 `InvalidSessionIdException`。

**关键点：这类异常重试同一个 `driver` 永远不可能成功。** 上游的"连续 3 轮异常才停"逻辑
在这里正好是反效果 —— 白烧 3 轮重试（每轮还 sleep 10 秒），然后整个任务终止，而视频才刷了一点点。

#### 根因（从崩溃转储里挖出来的）

崩溃转储落在 `%TEMP%\scoped_dir*\Crashpad\reports\*.dmp`（Windows 迷你转储，`MDMP` 格式）。
解析出来：

- 异常码 `0xC0000005`（ACCESS_VIOLATION），涉及模块 `msedge.dll`
- 崩溃偏移 `+0x556c74d`
- **17 个转储里，崩溃地址完全一致（17/17）** —— 这不是内存抖动、也不是随机竞争，是**确定性崩溃**

崩溃进程当时加载着整套硬件解码链：

```
mfx_mft_vp9ve_64.dll     Intel VP9 硬解 MFT
mfx_mft_h264ve_64.dll    Intel H264 硬解 MFT
igd11dxva64.dll          Intel D3D11 DXVA
igdgmm64.dll             Intel 图形内存管理
nvEncMFTH264x.dll        NVIDIA NVENC MFT
hevcdecoder_store.dll    系统 HEVC 解码器（Store 版）
d3d11.dll / dxgi.dll / mfplat.dll
```

指向 GPU/硬件解码路径。

#### 试过的处理

给浏览器加 7 个参数，把 GPU 与硬件编解码全关掉：

```
--disable-accelerated-video-decode
--disable-accelerated-video-encode
--disable-gpu
--disable-gpu-compositing
--disable-software-rasterizer
--disable-dev-shm-usage
--disable-features=CalculateNativeWinOcclusion
```

**A/B 实测结果**：崩溃地址**纹丝不变**（还是 `msedge.dll +0x556c74d`），
但崩溃前的存活播放量从约 147 秒提到约 593 秒（**约 4 倍**）。

也就是说这套参数**只是缓解，没有根除** —— 所以必须配上兜底。

#### 兜底：崩了就重建浏览器

主循环开头先探活，`force_restart` 或 `session_alive()` 为假就重建：

- `is_browser_gone()` 用一组特征串识别"会话已死"（`invalid session id` / `tab crashed` /
  `not connected to devtools` / `chrome not reachable` / `no such window` …）。
  命中的异常**不计入 3 次重试预算** —— 它根本不是"逻辑出错"
- `restart_browser()` 丢掉死会话 → 重建 driver → 走 `goto_course_page(allow_qr=False)` 回课程页。
  重建时**不弹扫码**（无人看守时没人扫），cookie 失效就明确报出来
- 视频进度记在**服务端**，重开后从断点续播，重建几乎不丢东西
- 连续重建 6 次仍跑不起来才真正停止，并明说"这是浏览器的问题，试试更新 Edge 或换 Chrome"

#### 顺带修掉的一个真 bug

`back_to_course_page()` 和 `leave_video_window()` 里关窗口之前，原先用的是**几行前拿的
`window_handles` 快照**。这一瞬站点可能已经自己把那个标签页关掉了，
此时 `close()` 关掉的就是**主窗口** —— 整个浏览器直接退出，下一轮就报 `InvalidSessionIdException`。

现在两处都在 `close()` 前**重新数一遍**窗口，`len(...) <= 1` 就跳过。

## 3. 2 倍速（这块最绕，单独说）

该站播放器**自带 2 倍速按钮，但那条 UI 路走不通**：用 CDP 原生鼠标事件确认可信点击确实打到了
倍速列表项（`isTrusted = true`、列表保持展开、`elementFromPoint` 确认无遮挡），
界面值和实际速率都纹丝不动。

真正的障碍是：播放器在 `ratechange` / `timeupdate` 里**把倍速同步回它自己内部的 1x 状态**，
大约每 250ms 一次。

让 agent 直接写 `video.playbackRate = 2` 是没用的 —— 实测 300ms 强制重设只能顶到 1.37x；
劫持 setter 读回来是 2、实际只有 1.35x，而且视频被暂停了。

**解法不是对抗，是"吞掉往低调的写入"**：给 `HTMLMediaElement.prototype.playbackRate`
装一层 setter，凡是想写到目标值以下的**直接丢弃不转发**。
被吞掉的写不改变实际值，因此不会再触发 `ratechange`，也就不会自激循环。
外面再加一个 1 秒定时器兜底补刀。

实测：12 秒内 `currentTime` 前进 23.6s / 墙钟 11.79s = **2.002x**，`paused = false`，
期间拦掉 49 次播放器的复位写入。

> **副作用**：播放器自己的 UI 仍显示 `1.00X`（它的内部状态没被改）。纯显示问题，不影响实际速率与切集。
> 判断真实速率请用 `currentTime` 的推进量，**不要读 `playbackRate`**。

## 4. 播放器的两个脾气

- **它会卸载重建 `<video>`。** 外层 `xt-wrap` 的 class 带上 `unload`，
  `document.querySelector("video")` 在开场会间歇性返回 `null`。
  上游代码依赖一个全局 `video` 变量，会对着已经脱离文档的僵尸元素操作（静音无效、倍速无效）。
  现在倍速锁 / 静音 / 暂停续播**全部改成元素无关** —— 每次现查现用。

- **它带防刷逻辑。** `blur` / `visibilitychange` 时若页面失焦或不可见就 `video.pause()`。
  无头模式下 `hasFocus()` 恒为 `true`、`hidden` 为 `false`，不受影响；
  有窗口模式下切走窗口就会被暂停，靠「暂停即续播」顶回去。
  `pause` 事件不冒泡，所以监听挂在 `document` 的**捕获阶段**。

另外无头模式必须加 `--autoplay-policy=no-user-gesture-required`，
否则 `video.play()` 会被浏览器的自动播放策略拦下来。

## 5. 配套脚本

| 文件 | 说明 |
|---|---|
| `run.bat` | 一键运行（自动设 `NO_PROXY` 绕开系统代理） |
| `refresh_cookie.py` / `refresh_cookie.bat` | 自动刷新 `config.ini` 里的 `sessionid` |
| `ChangjiangYuketang.spec` | PyInstaller 打包配置 |

`refresh_cookie.py` 有两条路径：优先**直接读本机 Firefox 的 cookie 库**
（Firefox 的 cookie 是明文 SQLite，只要 Firefox 里还登录着雨课堂就能秒取，不用扫码；
全程**只复制副本后以 `mode=ro` 查询，不修改 Firefox 任何文件**），
失败才回退到开浏览器扫码登录。出于凭据安全考虑，脚本**不回显 sessionid 内容**。
